# AGENTS.md

Poker Hold'em round simulation: a pure game engine + WebSocket server with a raylib GUI (all-in-one binary), with a WebSocket/JSON protocol (API.md) for remote clients. Git submodules under `thirdparty/`: `PokerHandEvaluator` (phevaluator, hand strength), `raylib`, `nlohmann` (JSON) and `libwebsockets` (v5.0.0, vendored). Linux, macOS and Windows.

## Commands

- `make` (root) — builds all three binaries: `server/build/server`, `bot/example/build/example_bot` and `client/build/client`. Parallel-safe (`make -j` splits sources into `.o` objects before linking). First build compiles the submodules via cmake (raylib takes minutes); phevaluator is configured with `-DBUILD_TESTS=OFF` (its upstream default fetches googletest/benchmark at configure time) and is built once up front before the parallel sub-makes start — server and bot/titan both need `libpheval.a`, and two concurrent cmake runs into the same `cpp/build/` dir corrupt each other. Equivalent to `make -C server bot/example client`. The raylib build is platform-configurable via `make RAYLIB_PLATFORM=wayland|x11|macos|windows`: when unset it is auto-detected — MSYS2/MinGW shells on Windows → `windows`, Darwin → `macos`, Linux with `XDG_SESSION_TYPE=wayland` (or `WAYLAND_DISPLAY` set) → `wayland`, other Linux → `x11`. Each platform builds into its own `thirdparty/raylib/build-<platform>/` directory, so switching backends needs no cache clearing. libwebsockets is vendored as a git submodule (`thirdparty/libwebsockets`, v5.0.0) and built from source via cmake with a minimal ws-only config (`-DLWS_WITH_SSL=OFF`, no extensions, no HTTP/2); no system lws packages are needed on any platform. On Windows, raylib's native Win32 backend is compiled with `-D_WIN32_WINNT=0x0A00 -DWINVER=0x0A00` (via `CMAKE_C_FLAGS` in `deps.mk`) because it calls Windows 10 DPI APIs (`GetDpiForWindow`, `AdjustWindowRectExForDpi`, `WM_GETDPISCALEDSIZE`) that MinGW only declares at that API level.
- Run the GUI server: `./server/build/server [--port 9000] [--host 127.0.0.1] [--token SECRET] [--max-players N] [--action-timeout N] [--simulate [MAX_SECONDS]] [--hand-pause N] [--scale N]` (loopback by default; `--host 0.0.0.0` for LAN); connect a random client: `./bot/example/build/example_bot --port 9000 [--token SECRET]`. See [HOW_TO_HOST.md](file:///home/hugo/code/poker/HOW_TO_HOST.md) for a full hosting guide (all flags, both game modes). `--headless` runs the same server without the raylib GUI (useful for debugging on a headless box). When the server runs with `--token`, clients must send the same token in `hello`. `--max-players` accepts 2–10 (default 6) and applies to both cash and tournament modes; the server validates the value and exits on bad input. `--action-timeout N` (default 20, min 1) sets the seconds a player has to act before the engine folds them. `--simulate` reintroduces human-like play server-side: every action from a bot (remote or auto-bot) is held for a uniform random 1.0..`MAX_SECONDS` s "thinking" delay (default max 3.0, must be ≥ 1.0) before it takes effect, capped just below the action deadline so a player who already answered is never folded on timeout — only players who never respond fold. Human clients are exempt: a client that says `hello` with `is_human: true` (the GUI client does) has its actions applied instantly, so the human never waits on the simulated delay (see API.md "hello"). The pause between hands is 0 without `--simulate` (hands chain instantly); with `--simulate` it defaults to 3.0 s and `--hand-pause N` (≥ 0) overrides it — `--hand-pause` without `--simulate` is an error. `--scale N` (0.5–2.0, default auto) sets the GUI scale level where 2.0 is the current look (cards 96×128, fonts 20 at 1280×720); without it the GUI auto-picks the largest of {2.0, 1.5, 1.25, 1.0, 0.75, 0.5} that fits the window and re-fits on resize (same flag on the client GUI).
- Tournament mode: `./server/build/server --tournament [--level-seconds N] [--countdown-seconds N] [--max-players N] [--tournament-end stay|exit|restart] [--tournament-end-hold N]` — no bots, the seats fill with connected clients, a countdown runs once the table is full, blinds/antes rise per level (schedule in API.md section 5), seats stay empty after a bust or disconnect, last player wins (winner-takes-all) and the server stays on the winner screen. `--tournament-end` picks the post-game behavior (default `stay` = winner screen, current behavior): `exit` stops the server (the GUI window closes, `run()` returns), `restart` kicks every client and resets to a fresh lobby after `--tournament-end-hold N` seconds on the winner screen (default 5, min 0; bots auto-reconnect and rejoin). Disconnected players are folded immediately (their chips stay in the pot) and busted at the next round end, not immediately. Tests drive it through `test/test_tournament.cpp` with tiny level/countdown durations and no action timeout.
- `./run_tournament.sh [N]` — convenience script that builds everything, starts an N-player tournament server in the background (N = seats, 2–10, default 6), launches N−1 bots (1 Titan `bot/titan`, 1 Python `bot/python` if N > 2, the rest C++ `bot/example`), and connects your human Raylib play client (`client/build/client`) in the foreground. Cleanly kills background bots upon exit.
- `make bot` (root) — builds `bot/example/build/example_bot` (a single-file remote client with a random person name like `Bob`, for the GUI server's remote seats) and `bot/titan/build/titan` (a stronger single-file bot: handcrafted Slumbot-style strategy — position-based preflop ranges, Monte-Carlo equity via phevaluator, pot-odds decisions, short-stack push/fold). Equivalent to `make -C bot/example` + `make -C bot/titan`. Both accept `--port/--host/--token/--name`; Titan also has `--selftest`.
- `make client` (root) — builds `client/build/client`, a raylib GUI play client (same table layout as the server GUI, own hole cards face up, other seats card-backed, Fold/Call/Raise buttons at the bottom). Connects to the server like a bot. Equivalent to `make -C client`.
- `make test` — builds and runs `test/build/test_poker`, `test/build/test_proto`, `test/build/test_server`, `test/build/test_tournament`, `test/build/test_pokerstars_export`: all tests in one binary each, **no per-test filtering** (they run in order in `main()`, each printing its own elapsed time). Run time is a few seconds: `test_server` shrinks the action timeout to 0.2 s, the hand-over pause to 0.01 s (`Server::hand_pause()`), and auto bots are given `think_seconds = 0`; `test_tournament` drives the tournament with no action timeout at all (players never fold on timeout) and tiny level/countdown durations. Pushed to GitHub, the `.github/workflows/tests.yml` workflow builds everything and runs `make test` plus `ci/smoke_game.sh` (a live headless game: real server + example bot over WebSocket) on four platforms — Linux X11, Linux Wayland, macOS and Windows (MSYS2/MinGW). Linux needs the raylib backend dev packages; Windows runs inside MSYS2 with `mingw-w64-x86_64-gcc`/`-cmake`. `test_server`/`test_tournament` use raw sockets only in `find_free_port()`, ported via `test/platform.h`.
- Tests include `../server/src/poker.h` and `../bot/example/bot.cpp` directly; plain `CHECK`/`CHECK_EQ` macros, no framework.
- **Engine bots act instantly**: `Player::ask_for_action` decides immediately (no thinking delay), and the remote `Bot` client no longer has any delay or indecision either (its `think_seconds` constructor parameter defaults to 0). Human-like pacing is the server's job: with `--simulate`, `Server::handle_action` queues every bot action into `pending_action_` and `step()` applies it after a uniform random 1.0..`simulate_max_` s hold (capped at `action_start + action_timeout - 0.05`); actions from human clients (`hello` `is_human: true`, stored on the `Session`) are applied immediately in `handle_action`. Tests run without `--simulate` at full speed and only `test_simulate_never_times_out` enables it (2 players, 0.2 s action timeout, min hold 1.0 s) to prove an answering player is never folded on timeout; `test_simulate_human_instant` proves a human client's actions skip the hold.
- GUI prints benign GLFW "Wayland: window position" warnings on stderr — not errors. The GUI uses whichever backend `RAYLIB_PLATFORM` selected (see the `make` bullet), so it needs a matching display session: Wayland for `wayland` (the common case), X11 for `x11`, and it runs natively on macOS/Windows.

## Architecture

The repo is split into two independent projects plus tests:

- `server/` — the whole game: engine, protocol, WebSocket server and raylib GUI.
  - `server/src/poker.h` / `server/src/poker.cpp` — pure engine, no raylib. Everything runs through `Table::step_game(&state, now)`, driven with a monotonic `now`; `Game_State` is the engine/UI boundary.
  - `server/src/server_main.cpp` — raylib GUI + WebSocket server entry point: creates `Server srv(port, host, token)`, drives it with `srv.tick(GetTime())` every frame (lws_service + engine step + event detection), and draws the table; card art built from `decks/jorels`, all cards visible (the binary cd's up to the repo root to find `decks/`).
  - `server/src/card.h` — raylib UI card renderer. Confusingly similar to `phevaluator::Card` (the type the engine uses everywhere); do not mix them.
  - `server/src/server.cpp` / `server/src/server.h` — WebSocket server. `run()` is the headless loop (used by tests); the GUI entry uses `tick(now)` instead. Broadcasts a full state snapshot to all clients whenever the turn changes, plus targeted `your_turn` messages. Seat changes only happen at the end of a round: `hello` reserves a bot seat (`queued`), the client takes over with a full entry stack when the round ends (`welcome`); clients leaving mid-hand are folded and a bot resumes the seat at the next round end. `set_simulate()` queues every bot action in `pending_action_` (a single slot; a new action overwrites it, and `disconnect()` clears it) so `step()` can hold it for the random "thinking" delay (human clients with `hello` `is_human: true` skip the queue and act instantly); auto bots are held the same way via `hold_seat_`/`hold_until_` (1.0 + `poker_random()*(simulate_max_-1.0)`). In tournament mode, a disconnected player is folded immediately and their bust is deferred to the next `process_round_end()` call via a `pending_bust_` flag — this keeps their chips in the pot for the current hand before they are eliminated.
  - `server/src/proto.{h,cpp}` — the API.md protocol layer (message parsing, validation, state JSON). Uses nlohmann + the engine.
- `bot/` — independent clients: WebSocket + JSON only (API.md), **no engine/protocol headers**. See [HOW_TO_BOT.md](file:///home/hugo/code/poker/HOW_TO_BOT.md) for a guide on writing a custom bot. `bot/example/bot.cpp` is the single-file C++ client (standalone binary, or a test client when `test/test_server.cpp` includes it without `-DBOT_EXAMPLE_STANDALONE`); `bot/python/bot.py` is the same bot in Python (`bot/python/venv` holds its deps, run `venv/bin/python bot.py`). Both are intentionally small examples of the API.md protocol, meant to be extended into smarter bots. `bot/titan/bot.cpp` is a competitive single-file bot with the same transport but a handcrafted Slumbot-style strategy (position-based preflop range tables, Monte-Carlo equity via the phevaluator submodule, pot-odds decisions, short-stack push/fold).
- `client/` — human-play GUI client: a raylib window on top of `bot/example/bot.cpp` (included as a library, `auto_play = false`). Same table layout as the server GUI but only the player's own hole cards (`query` `my_cards`) are shown face up; other seats draw `decks/jorels/card_back.png`. Manual actions come from the Fold/Call/Raise buttons at the bottom.
- `API.md` — all API calls (client→server actions, server broadcasts, queries, error codes) are described in `API.md`: a WebSocket/JSON protocol spec for remote clients. `Player::ask_for_action(const Game_State*)` is the hook bots use to answer; keep its signature.
- Rules constants in `server/src/poker.h`: SmallBlind 5, BigBlind 10, StartStack 1000, ActionTimeOut 20 s, MaxPlayers 10 (hard cap; the default table is 6). Both modes support 2–10 players via `--max-players`; the engine's `Table::new_hand` no longer asserts exactly 6 players. Both GUIs arrange seats on an ellipse computed from the table size (seat 0 top, clockwise; the client always draws the hero bottom centre).
- `deps.mk` — shared make rules for the thirdparty submodule libraries (raylib, phevaluator, libwebsockets), included by the root, server, client and bot/example Makefiles.

## Gotchas

- `phevaluator::Card` has no default constructor: `std::map::operator[]` does not compile — use `emplace`/`at`.
- `Player::rank` is private: read hand strength via `hand_value()` (1 = best … 7462 = worst), `describe_category()`, `describe_rank()`; `set_rank()` is only called by `Table::recalc_player_hand_strength()`.
- Bots have `auto_play = true` and answer through `ask_for_action`; non-auto players just fold on timeout. Players busted to 0 chips are rebought to `StartStack` in `end_hand`.
- `Player::last_action` persists for the whole betting round (like `_fold`); it is reset in `start_betting_round` and `end_hand`, not on re-raises.
- Seeded determinism for tests/experiments: `poker_set_seed(unsigned)`.
- **`/usr/include/lws_config.h` is a silent ABI trap** (if libwebsockets-dev is installed). The vendored build is a minimal ws-only config; its generated `thirdparty/libwebsockets/build/include/lws_config.h` differs hugely from the system one, and the system config changes `lws_context_creation_info`'s layout (e.g. `user` moves from +0xc8 to +0x1d0). If a TU that includes `libwebsockets.h` compiles before that header exists (a fresh `thirdparty/libwebsockets/build` racing a parallel `make`), g++ silently falls back to the system config: compiles fine, then crashes on the first client connection (`lws_context_user` returns NULL → NULL `srv` → segfault in `server_callback`). All object rules depend on `$(LWS_LIB)` so the vendored config always exists first, and `#if defined(LWS_WITH_HTTP2) #error ...` tripwires in `server.h` and both bots fail the compile loudly if the system config is ever picked up again.
- **`lws_service()` ignores its timeout argument** (blocking since lws 3.2) on both server and client contexts. Any loop that needs to keep stepping (GUI `Server::tick()`, test loops pumping a client context) must have a ticker thread calling `lws_cancel_service()` ~every 16 ms — the server has one built in, client contexts in tests need their own.
- **The server's `LWS_CALLBACK_SERVER_WRITEABLE` handler drains the whole session out-queue in one callback.** The classic "write one message, re-arm with `lws_callback_on_writable()`, write the next" pattern stalls on idle connections (the re-armed writable never fires, e.g. a tournament seat that only ever received `welcome` + `state`). The client bot (`Bot::flush`) can keep the one-at-a-time pattern because tests always drive further sends.
- Broadcasts to a client are queued and only delivered on the next lws service round, so a test that checks `g_msgs` right after a `wait_until` on a server-side flag (e.g. `busted`, `tournament_status`) races a frame ahead of the message — assert on the message itself (`wait_until` over `seen()`/`g_msgs`), not on the flag then the queue.
- **A client-side ws wsi closes with `LWS_CALLBACK_CLIENT_CLOSED` (75), not `LWS_CALLBACK_CLOSED`** (that fires only for server-side wsi). Without the former, a bot/client never notices the connection dying and keeps a dangling `wsi_`. When the server busts a seated player, `process_round_end()` kills the session (`lws_set_timeout(...LWS_TO_KILL_ASYNC)`) and the seat reverts to an auto bot; clients must handle `LWS_CALLBACK_CLIENT_CLOSED` to detect it. The GUI client closes the window in that case.
- **`~Bot()` nulls the wsi's userdata before killing it** (`lws_set_wsi_user(wsi, nullptr)` + `LWS_TO_KILL_ASYNC`) and the callback returns early on a null `user`. Deleting a `Bot` without that (or keeping callbacks pointing at freed memory) makes a later close callback write `wsi_ = nullptr` into whatever new object reuses the freed chunk — a live bot suddenly "disconnects", reconnects, and ends up with two sessions (double broadcasts, `table_full`, `unauthorized`, phantom timeout folds).
- **Tournament disconnect is graceful**: a disconnecting player is folded immediately (if still in the hand) so the pot resolves normally, but `busted` is only set in `process_round_end()` after `end_hand()`. The `pending_bust_` vector in `Server` tracks these deferred eliminations. Do not test `player.busted` immediately after a disconnect — wait for the `player_out(disconnected)` broadcast instead.
- **`Table::award_pots(int dealer)`** takes the dealer seat so the odd chip from a split goes to the first winner clockwise from the dealer. Always call it via `finish_hand()` (which passes `state->dealer`); don't call it directly.
