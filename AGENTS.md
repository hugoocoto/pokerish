# AGENTS.md

Poker Hold'em round simulation: a pure game engine + WebSocket server with a raylib GUI (all-in-one binary), with a WebSocket/JSON protocol (API.md) for remote clients. Git submodules under `thirdparty/`: `PokerHandEvaluator` (phevaluator, hand strength), `raylib` and `nlohmann` (JSON). Linux/Wayland only.

## Commands

- `make` (root) — builds all three binaries: `server/build/server`, `bot/example/build/example_bot` and `client/build/client`. Parallel-safe (`make -j` splits sources into `.o` objects before linking). First build compiles the submodules via cmake (raylib takes minutes). Equivalent to `make -C server bot/example client`.
- Run the GUI server: `./server/build/server [--port 9000] [--host 127.0.0.1] [--token SECRET] [--max-players N]` (loopback by default; `--host 0.0.0.0` for LAN); connect a random client: `./bot/example/build/example_bot --port 9000 [--token SECRET]`. `--headless` runs the same server without the raylib GUI (useful for debugging on a headless box). When the server runs with `--token`, clients must send the same token in `hello`. `--max-players` accepts 2–6 and applies to both cash and tournament modes; the server validates the value and exits on bad input.
- Tournament mode: `./server/build/server --tournament [--level-seconds N] [--countdown-seconds N] [--max-players N]` — no bots, the seats fill with connected clients, a countdown runs once the table is full, blinds/antes rise per level (schedule in API.md section 5), seats stay empty after a bust or disconnect, last player wins (winner-takes-all) and the server stays on the winner screen. Disconnected players are folded immediately (their chips stay in the pot) and busted at the next round end, not immediately. Tests drive it through `test/test_tournament.cpp` with tiny level/countdown durations and no action timeout.
- `./run_tournament.sh` — convenience script that builds everything, starts a 6-player tournament server in the background, launches 3 C++ bots (`bot/example`) and 2 Python bots (`bot/python`), and connects your human Raylib play client (`client/build/client`) in the foreground. Cleanly kills background bots upon exit.
- `make bot` (root) — builds `bot/example/build/example_bot` (a single-file remote client with a random person name like `Bob`, for the GUI server's remote seats). Equivalent to `make -C bot/example`.
- `make client` (root) — builds `client/build/client`, a raylib GUI play client (same table layout as the server GUI, own hole cards face up, other seats card-backed, Fold/Call/Raise buttons at the bottom). Connects to the server like a bot. Equivalent to `make -C client`.
- `make test` — builds and runs `test/build/test_poker`, `test/build/test_proto`, `test/build/test_server`, `test/build/test_tournament`: all tests in one binary each, **no per-test filtering** (they run in order in `main()`, each printing its own elapsed time). Run time is a few seconds: `test_server` shrinks the action timeout to 0.2 s, the hand-over pause to 0.01 s (`Server::hand_pause()`), and auto bots are given `think_seconds = 0`; `test_tournament` drives the tournament with no action timeout at all (players never fold on timeout) and tiny level/countdown durations. Pushed to GitHub, the `.github/workflows/tests.yml` workflow runs the same `make test` (submodules included, needs `libwebsockets-dev`/`libcap-dev`/`libsystemd-dev`).
- Tests include `../server/src/poker.h` and `../bot/example/bot.cpp` directly; plain `CHECK`/`CHECK_EQ` macros, no framework.
- **Engine bots act instantly**: `Player::ask_for_action` decides immediately (no thinking delay). The ~1 s "thinking" delay + 40% indecision (per try) lives in the remote `Bot` client (bot/example/bot.cpp `pump`); its `think_seconds` constructor parameter (default 1.0, 0 = instant) lets tests play without the delay.
- GUI prints benign GLFW "Wayland: window position" warnings on stderr — not errors. GLFW is built Wayland-only (no X11), so the GUI needs a Wayland session.

## Architecture

The repo is split into two independent projects plus tests:

- `server/` — the whole game: engine, protocol, WebSocket server and raylib GUI.
  - `server/src/poker.h` / `server/src/poker.cpp` — pure engine, no raylib. Everything runs through `Table::step_game(&state, now)`, driven with a monotonic `now`; `Game_State` is the engine/UI boundary.
  - `server/src/server_main.cpp` — raylib GUI + WebSocket server entry point: creates `Server srv(port, host, token)`, drives it with `srv.tick(GetTime())` every frame (lws_service + engine step + event detection), and draws the table; card art built from `decks/jorels`, all cards visible (the binary cd's up to the repo root to find `decks/`).
  - `server/src/card.h` — raylib UI card renderer. Confusingly similar to `phevaluator::Card` (the type the engine uses everywhere); do not mix them.
  - `server/src/server.cpp` / `server/src/server.h` — WebSocket server. `run()` is the headless loop (used by tests); the GUI entry uses `tick(now)` instead. Broadcasts a full state snapshot to all clients whenever the turn changes, plus targeted `your_turn` messages. Seat changes only happen at the end of a round: `hello` reserves a bot seat (`queued`), the client takes over with a full entry stack when the round ends (`welcome`); clients leaving mid-hand are folded and a bot resumes the seat at the next round end. In tournament mode, a disconnected player is folded immediately and their bust is deferred to the next `process_round_end()` call via a `pending_bust_` flag — this keeps their chips in the pot for the current hand before they are eliminated.
  - `server/src/proto.{h,cpp}` — the API.md protocol layer (message parsing, validation, state JSON). Uses nlohmann + the engine.
- `bot/` — independent clients: WebSocket + JSON only (API.md), **no engine/protocol headers**. See [HOW_TO_BOT.md](file:///home/hugo/code/poker/HOW_TO_BOT.md) for a guide on writing a custom bot. `bot/example/bot.cpp` is the single-file C++ client (standalone binary, or a test client when `test/test_server.cpp` includes it without `-DBOT_EXAMPLE_STANDALONE`); `bot/python/bot.py` is the same bot in Python (`bot/python/venv` holds its deps, run `venv/bin/python bot.py`). Both are intentionally small examples of the API.md protocol, meant to be extended into smarter bots.
- `client/` — human-play GUI client: a raylib window on top of `bot/example/bot.cpp` (included as a library, `auto_play = false`). Same table layout as the server GUI but only the player's own hole cards (`query` `my_cards`) are shown face up; other seats draw `decks/jorels/card_back.png`. Manual actions come from the Fold/Call/Raise buttons at the bottom.
- `API.md` — all API calls (client→server actions, server broadcasts, queries, error codes) are described in `API.md`: a WebSocket/JSON protocol spec for remote clients. `Player::ask_for_action(const Game_State*)` is the hook bots use to answer; keep its signature.
- Rules constants in `server/src/poker.h`: SmallBlind 5, BigBlind 10, StartStack 1000, ActionTimeOut 20 s, MaxPlayers 6. Both modes support 2–6 players via `--max-players`; the engine's `Table::new_hand` no longer asserts exactly 6 players.
- `deps.mk` — shared make rules for the thirdparty submodule libraries (raylib, phevaluator), included by the root, server and client Makefiles.

## Gotchas

- `phevaluator::Card` has no default constructor: `std::map::operator[]` does not compile — use `emplace`/`at`.
- `Player::rank` is private: read hand strength via `hand_value()` (1 = best … 7462 = worst), `describe_category()`, `describe_rank()`; `set_rank()` is only called by `Table::recalc_player_hand_strength()`.
- Bots have `auto_play = true` and answer through `ask_for_action`; non-auto players just fold on timeout. Players busted to 0 chips are rebought to `StartStack` in `end_hand`.
- `Player::last_action` persists for the whole betting round (like `_fold`); it is reset in `start_betting_round` and `end_hand`, not on re-raises.
- Seeded determinism for tests/experiments: `poker_set_seed(unsigned)`.
- **`lws_service()` ignores its timeout argument** (blocking since lws 3.2) on both server and client contexts. Any loop that needs to keep stepping (GUI `Server::tick()`, test loops pumping a client context) must have a ticker thread calling `lws_cancel_service()` ~every 16 ms — the server has one built in, client contexts in tests need their own.
- **The server's `LWS_CALLBACK_SERVER_WRITEABLE` handler drains the whole session out-queue in one callback.** The classic "write one message, re-arm with `lws_callback_on_writable()`, write the next" pattern stalls on idle connections (the re-armed writable never fires, e.g. a tournament seat that only ever received `welcome` + `state`). The client bot (`Bot::flush`) can keep the one-at-a-time pattern because tests always drive further sends.
- Broadcasts to a client are queued and only delivered on the next lws service round, so a test that checks `g_msgs` right after a `wait_until` on a server-side flag (e.g. `busted`, `tournament_status`) races a frame ahead of the message — assert on the message itself (`wait_until` over `seen()`/`g_msgs`), not on the flag then the queue.
- **A client-side ws wsi closes with `LWS_CALLBACK_CLIENT_CLOSED` (75), not `LWS_CALLBACK_CLOSED`** (that fires only for server-side wsi). Without the former, a bot/client never notices the connection dying and keeps a dangling `wsi_`. When the server busts a seated player, `process_round_end()` kills the session (`lws_set_timeout(...LWS_TO_KILL_ASYNC)`) and the seat reverts to an auto bot; clients must handle `LWS_CALLBACK_CLIENT_CLOSED` to detect it. The GUI client closes the window in that case.
- **Tournament disconnect is graceful**: a disconnecting player is folded immediately (if still in the hand) so the pot resolves normally, but `busted` is only set in `process_round_end()` after `end_hand()`. The `pending_bust_` vector in `Server` tracks these deferred eliminations. Do not test `player.busted` immediately after a disconnect — wait for the `player_out(disconnected)` broadcast instead.
- **`Table::award_pots(int dealer)`** takes the dealer seat so the odd chip from a split goes to the first winner clockwise from the dealer. Always call it via `finish_hand()` (which passes `state->dealer`); don't call it directly.
